# 费用查询与分析

先确认用户要得到的结果，再按以下步骤选择接口、采集数据和分析。已有适用查询结果时，
直接从结果检查或分析步骤继续。命令路径相对 Skill 根目录；在其他目录执行时使用
`<skill-root>/scripts/cost.py` 的实际路径，分析文件写入任务目录。

按用户目标确定最小结果和下一步；组合问题继续处理未回答的部分：

| 用户目标 | 先取得或计算 | 何时继续 |
|---|---|---|
| 查金额、看样本或导出 | 指定范围和金额口径的数据；未指定口径的普通费用查询使用应付金额并说明 | 样本不扩成全量；导出按用户范围完成 |
| 看趋势或 TopN | 同口径时间序列或分组金额 | 只问走势/排名时交付结果，无需自动归因 |
| 解释费用变化 | 对齐窗口后的总变化、对象变化及贡献 | 按[费用变化分析](cost-change-analysis.md)选择分析能力并取证 |
| 查资源包或券状态、抵扣记录 | 指定对象或产品、时间范围内的库存/记录 | 需要解释未抵扣或抵扣减少时进入[账户欠费与抵扣核查](arrears-analysis.md)中的资源包或代金券流程 |
| 查当前余额或是否欠费 | [账户欠费与抵扣核查](arrears-analysis.md)中的当前账户状态所需数据 | 给出当前资金快照，不扩展为历史状态 |
| 谁替账号付账、财务托管或成员费用归属 | [财务托管与付费归属](financial-relations.md)所需关系或账单事实 | 只问关系时不查余额；需要金额时保持使用方和付费方筛选 |
| 查账单未还款构成 | [账户欠费与抵扣核查](arrears-analysis.md)中的未还款构成所需数据 | 按指定账期解释，不要求先查账户状态 |
| 解释当前欠费原因 | [账户欠费与抵扣核查](arrears-analysis.md)中的当前欠费原因分析所需数据 | 先确认账户欠费，再按消费线索选择子流程 |
| 正式核对两份账务来源的金额一致性 | 两侧同范围的查询产物 | 优先复用[聚合对账](cost-reconciliation.md) |

用户已给范围时保持原范围。普通月账单查询未给账期时，从当前账期开始并在回答中说明。
用户指定比较已有文件时保留其快照，缺正式 metadata 不等于必须重新查询；重新查询产生
新输入时说明变更，不把新结果当成原文件的分析。
“为什么涨了”未给基期时，已结束月份可与上月比较。当前月优先比较相同已覆盖日期，只有
对应字段和数据能支持时才这样计算；无法对齐时先报告已知金额和窗口差异。歧义会改变
金额口径或明显扩大查询范围时，向用户确认缺少的参数。

## 1. 确认接口与字段粒度

复用仍符合本次账号、口径、时间、粒度和时效要求的 Action 与契约；缺少执行依据时，
一次补齐所需信息。

无法确定 Action 时，读取一次能力目录：

```bash
python3 scripts/cost.py schema --list-actions
```

选定 Action 后，如果尚无适用的请求契约，一次加载该 Action 的请求规则和业务指引：

```text
python3 scripts/cost.py schema --action <Action> --section request --include-guidance
```

据此确定合法字段、枚举、组合规则和必要粒度，再构造查询。`query describe` 和 help
用于补充尚未明确的执行参数或输出协议，不是每次查询的固定步骤。

响应解释优先复用已经加载的响应契约或本次 fields artifact。关键字段含义缺失且会改变
请求或结论时，把需要确认的字段合并为一次查询：

```text
python3 scripts/cost.py schema --action <Action> --section response --field <Field1>,<Field2>
```

确实不知道字段名并需要探索响应结构时，才读取完整 response。

检查必要字段能否在请求粒度保留。字段存在 `response_field_decisions` 时，先用
`available_request_values` 检查候选参数；合法值保持原样，不合法时才用
`required_request` 修复。多个字段的约束无法同时满足时，重新选择粒度或 Action。
没有字段级决策只表示未登记专门规则，实际响应仍需核验。

执行时为必要字段传入 `--require-field <Field>`，可重复使用，让执行器在请求前统一校验。
尤其需要用量、单价、实例或明细标识时，不能先聚合丢失字段再尝试从结果推回。

选择数据来源时保留以下区别：

- 账单/明细反映原始账务；分账用于项目、标签等归属解释；摊销成本按实际使用周期分摊。
  原始账期和分摊月/日是不同时间轴。普通账单由 `BillPeriod` 决定记录的出账归属；
  `ExpenseBeginTime`/`ExpenseEndTime` 表示实例实际使用周期，可能晚于出账账期甚至位于未来，
  但不改变记录的账期归属。需要按实际使用日期或月份查看成本时，使用月度、每日或明细分摊
  成本 Action；`AmortizedMonth`/`AmortizedDay` 决定成本归属，`BillPeriod` 只追溯原始账期。
- 普通账单的使用周期字段可以解释费用覆盖时间，不能用于从账期合计中排除记录，也不能把
  整笔账单金额手工归入开始日期所在的日或月。用户只问实例何时开始或结束使用时读取账单
  明细；用户问实际使用日/月的成本金额时改查分摊成本账单。
- 账单明细到分账明细是一对多分拆。成本明细没有与账单明细逐条关联的稳定键，字段
  相似不能证明可以 Join。
- `ListCostAnalysisOpenApi` 在账单明细出具后 T+2 日更新，且单次只支持一个分类维度。
  需要最新明细、多维关系或逐条证据时，选择能保留这些关系的行数据 Action。
- 分账和成本通常比账单明细延迟约 2 天，项目/标签还可能再延迟约 12 小时；按实际
  freshness 限定结果时点。任何账单查询均不证明账户或资源的实时费用。

## 2. 确定范围并查询

执行前在内部明确 Action 与理由、时间范围、金额字段、筛选条件、必要字段、采集范围
和后续计算。信息足够时直接执行；用户要求计划或复现方式时再展示这些依据。

分页 Action 显式选择 `page` 或 `full`：预览、指定页和抽样用 page；准确汇总、全量
排名、完整导出和对账用 full。一次返回的 Action 自动完整采集；传入分页参数时会忽略
并返回 warning，处理该提示即可。

```text
python3 scripts/cost.py query --action <Action> --body '<JSON business request body>' --pagination <page|full>
```

长 body 使用 `--body-file`；`--page-size` 设置每页大小，不是 full 的总条数上限。
单页模式按指定页大小请求，不自动缩页；页大小超过 `--max-rows` 时，查询前报参数冲突。
接口返回后展开的行数仍可能超过上限，此时只交付上限内的数据，并返回 `partial`、退出码 6
和范围缺口。需提高上限重查当前页，不能把裁切结果视为完整请求页。
Limit/Offset 分页通过 `--page-offset` 定位页，full 从 Offset=0 开始；支持 NeedRecordNum
的 Action 按契约开启总数查询。NextToken 分页在 body 提供 token，full 从空 token 开始，
不传 `--page-offset`。body 与 CLI 中同时提供的页大小或偏移须一致，翻页检查由执行器负责。
单页响应的续页游标见 `coverage.queries[].next_token`，`has_more` 表示是否还有下一页。
inline 输出在 `_meta.coverage`，文件输出在对应 metadata 的 `coverage` 中读取。

查询多个账期时，支持 BillPeriod 或 AmortizedMonth 的 Action 用 `--period YYYY-MM`
为每个账期分别指定月份，成功账期进入同一结果并保留各账期证据。
其他时间字段按 Action 请求契约直接传入 body，不套用账期替换。
跨期比较先确定所需分析期与基期。

需要固定文件名或持久保存原始数据时加 `--out <task-result>.csv`；否则由结果大小决定
直接返回数据或自动写入结果文件。使用任务专属路径。遇到 OUTPUT_EXISTS，换新路径，或在确认所有
冲突产物属于本任务且可替换后使用 `--overwrite`，保持原查询范围。

## 3. 检查结果与读取数据

所有 Action 使用相同的 `status/message/result`：
- `result` 存放业务数据；文件型结果直接包含 `file`、`metadata`、`fields` 三个绝对路径，
  可作为其他原子工具的结构化输入；
- `message` 说明页范围、当前账期、合法空结果和失败限制。
- `status=success` 时在 `message` 声明的范围内使用结果；`status=partial` 时只解释已经交付的
部分，并按 `message` 决定补查或降级；`status=error` 时不使用 `result` 形成业务结论。非零
退出码仍可能携带 `partial` 结果，不能丢弃 stdout。

参数错误读取 `_meta.error.details.invalid_parameters`：每项只描述错误参数、违反约束及其局部真实契约；
参数存在于 Action schema 时还会附实际值，未知参数不回显实际值，避免泄露可能混入的凭证。
这不代表其他参数必须复用，也不构成后续执行计划。Agent 根据任务上下文自主决定
修正参数、重新发现、重新调用或终止。需要错误码和退出码时读取
`cost.py query describe --section errors`。

## 4. 解释字段与分析结果

优先使用已加载的响应契约或本次 fields artifact，确认字段的 description、role、
aggregations、currency_field 和可用粒度。未知新增字段可以保留，但须确认含义后才
用于业务解释；已知字段类型错误由执行器报告，已屏蔽字段不恢复。

`PaidAmount`、`UnpaidAmount`、`CreditCarriedAmount` 仅在 BILL 三个 Action
（ListBill、ListBillOverviewByProd、ListBillOverviewByCategory）解释：

- PaidAmount 是现金支付，不等于所有支付方式或账户总扣款。
- UnpaidAmount 是已出账未还款金额，不证明账户实时欠费。
- CreditCarriedAmount 保留正负号：正值为信控退款抵减欠款，负值的绝对值为信控退款金额。

明细、分账和成本响应中的对应字段族已屏蔽，不从其他字段反推被屏蔽的值。原价、折后价、
应付与抹零使用各自真实字段，不能因显示精度不同而互相替代。

按用户目标直接编写数据处理代码；需要时按需使用公共 helper。遵循以下分析原则：

1. **可比性**：确认金额含义、币种、粒度和时间窗口。正式对账要求可比；用户指定不同
   范围做观察性比较时保留原范围并说明差异。当前部分月份不能等同完整月份。基期为零或
   负数时明确比例定义，不输出无定义的增长率。
2. **精度**：金额从原始字符串进入 Decimal，不先转 float。保留负号和原始精度，缺失
   不补零；一组金额全缺失时汇总保持未知，部分缺失时说明有效输入范围。
3. **聚合**：不同币种和单位分开计算与排名，单价/比例不直接求和；平均单价按可比用量
   加权。用户要求格式化时明确舍入规则，不把展示舍入用于后续计算。
4. **关联**：明确每份输入、关联键、数据粒度和关联关系，保留账号/实例标识中的前导零。
   检查重复键、未匹配记录和金额放大；多对多关联需要明确分配或聚合规则，同名字段不自动
   代表相同业务实体。
5. **核验**：按实际筛选范围核对聚合前后金额、行数和缺失记录；TopN 核对排序、条数
   与对应子集，不能宣称其覆盖整体。多层分析保留中间计算依据。
6. **证据范围**：`status=partial` 和 `message` 指出的页范围、当前期及其他限制随派生结果
   保留，多来源结论受各必需输入共同限制。生成新文件不会提升原始数据的完整性。

根据用户目标选择聚合、Join 或其他分析方法；适合正式对账时优先复用
[聚合对账](cost-reconciliation.md)，不因两侧 Action 已登记关系就强制进入该流程。
结果保留各输入的范围、完整性和语义限制；自定义分析产物不能冒充原始 query 产物供
reconcile 使用，也不能将观察性比较表述为标准对账结果。

## 5. 交付

普通查询给出核心结果、必要的金额口径/关键筛选和范围限制；API 名称通常留在复现材料中。
full、TopN 或求和本身不要求生成派生文件。没有生成文件时只交付结果。

金额查询报告所选范围和币种；样本汇总标明当前页；趋势或变化分析报告比较窗口、差额和
主要对象。复杂问题先回答各子问题，再说明会改变结论的限制，避免以执行过程代替业务回答。

用户需要文件时给出实际产物路径；需要复现时保存输入引用、筛选与口径、计算脚本、结果
和必要限制，让同一输入可以重算。引用原始查询的证据信息时保留其身份范围、时效和失败信息，
不伪造新的查询证据。
