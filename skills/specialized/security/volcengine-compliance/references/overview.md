# 合规总览：结果解读与严重度定级

合规总览（`compliance.py overview`）汇总账号**当前**已生效规则/合规包的评估结果，按合规类别与
严重度聚合成报告。本 reference 是报告的判读口径。

## 覆盖范围：内置 + 自定义一视同仁

总览统计账号里**全部 `Enabled` 的规则**，不区分来源：

- 官方内置基线部署出来的规则（来源 `BuiltIn`）。
- 用户自己创建的规则 / 自定义合规包（来源 `Custom`）。

每条不合规结果都标注 `Source`（BuiltIn / Custom）与 `Category`（法规合规 / 最佳实践 /
自定义），但**不因来源而过滤**——合规态势是账号的整体状况。

## 合规类别怎么判定

- 规则所属合规包命中某官方内置模板 → 归该模板的类别（法规合规 / 最佳实践），来源 `BuiltIn`。
- 否则归「自定义」类别，来源 `Custom`。

报告正文按类别分节，节内再按严重度降序。

## 合规状态

火山配置审计的评估结果状态（ComplianceType）：

| 状态 | 含义 |
| --- | --- |
| `Compliant` | 资源符合规则 |
| `NonCompliant` | 资源不符合规则（报告核心关注对象） |
| `Exempt` | 资源被豁免，不计入不合规 |
| `Error` | 评估执行出错 |
| `Insufficient` | 数据不足，暂无法判定（新资源常见） |

总览按 `NonCompliant` 过滤，`Exempt` 是独立状态**天然被排除**，不会误报。

## 严重度定级

规则风险等级（RiskLevel）三档，映射到报告的四档严重度：

| 规则 RiskLevel | 报告 Severity | 处理建议 |
| --- | --- | --- |
| `High` | **Critical** | 高影响暴露，立即处理 |
| `Medium` | **High** | 数天内处理 |
| `Low` | **Medium** | 排进下个迭代 |
| 缺失/未知 | **Unknown** | 需人工确认规则风险定义 |

## 排序与汇报

- 报告按 **严重度优先、其次不合规资源数** 倒序排列。
- 汇报时先给结论（「评估 N 条规则，M 条不合规，X 个 Critical」），再逐条讲 Critical / High，
  避免用户被低优先级淹没。

## 报告结构

`compliance.py overview` 产出三份产物：

- `compliance-overview-*.md`：人读报告（摘要 + 严重度分布 + 类别分布 + 按类别分节的明细）。
- `compliance-findings-*.csv`：不合规资源逐行明细（含 Category / Source 列），便于导表。
- `compliance-overview-*.json`：结构化数据，便于二次处理。

stdout 只回摘要 + 产物路径；用 Read 工具读 md 产物向用户汇报，不要 `cat` 整个文件。

## 报告 vs 修复

- 报告只呈现「哪里不合规、要求是什么、建议怎么改」。
- **修复动作**（改资源配置 / 触发自动修正）**不在报告阶段执行**，作为整改建议给出，由用户
  确认后另行操作。合规「报告」与「修复」严格分离——这是合规工作的基本纪律。

## 常见判读问题

- **总览无结果 / 全是 Insufficient**：资源评估异步进行，部署完不等于立刻有结果；稍等再跑。
  账号若尚无已生效规则，先用 `recommend` 看该开哪些、再 `apply` 部署。
- **某规则状态 `Error`**：评估执行出错（权限/快照缺失等），不是「不合规」。当前报告聚焦
  `NonCompliant`，如需看 Error 需单独查。
- **不合规数为 0 但用户觉得应该有**：确认规则是否 Enabled、资源是否已被评估、Scope 是否把
  目标资源过滤掉了。
- **明细太多**：`overview --max-resources` 限制每规则明细条数（默认 200），完整明细看 CSV。
